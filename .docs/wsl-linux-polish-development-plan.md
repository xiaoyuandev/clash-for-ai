# WSL / Linux Web Polish 开发计划

## 文档目的

这份文档用于把以下清单收敛成新的优化开发计划：

1. [.docs/wsl-linux-polish-checklist.md](/Users/yuanjunliang/Documents/workspace/profile/clash-for-ai/.docs/wsl-linux-polish-checklist.md:1)

这是一份专门面向 WSL / Linux 补充入口的 polish 计划。

它的目标不是扩功能边界，而是：

1. 提升 Web 端状态可理解性
2. 提升 WSL / Linux 场景下的使用体验
3. 清理 Web 端残留的桌面端心智

后续如果要执行这轮优化，应以本计划文档作为开发基线。

## 最高优先级原则

整个计划必须始终遵守以下原则：

1. `Electron` 仍是本地主入口
2. `Web / PWA` 是 WSL 和 Linux server 的补充入口
3. 当前桌面端功能已经稳定，本轮 polish 只优化 Web 端
4. 不允许为了 Web 端 polish 破坏桌面端现有功能
5. `Go core` 仍然是唯一业务中心

这五条原则高于具体实现便利性。

## 本轮范围

本轮计划只覆盖以下方向：

1. Web 端统一运行状态总览
2. `Tools` 页顶部状态语义修正
3. Web 小屏 / 窄屏导航体验优化
4. Web 端残留桌面心智清理
5. 文档补充 `ai-mini-gateway` 二进制准备说明
6. 评估是否需要 `GATEWAY_BIND` 配置项
7. 左侧底部语言/主题区的实验性紧凑化优化

## 本轮明确不做

本轮不做以下内容：

1. 不新增新的后端服务层
2. 不改变 Electron 主入口定位
3. 不为 `LOCAL_GATEWAY_RUNTIME_EXECUTABLE` 增加前端提示
4. 不做页面头部 sticky
5. 不做大规模目录重构
6. 不引入新的状态管理库
7. 不为了 Web 端需求修改桌面端成熟交互

## 当前确认结论

根据已经确认的评估，这些项的处理方式如下：

### 1. `LOCAL_GATEWAY_RUNTIME_EXECUTABLE` 未配置前端提示

处理方式：

1. 当前暂缓前端提示改造
2. 优先依赖文档说明
3. 后续优先靠安装脚本自动配置

因此这项不进入本轮开发。

### 2. 页面头部 sticky

处理方式：

1. 当前移出本轮

原因：

1. 左侧导航已有高亮锚点
2. 右侧头部较大，sticky 会持续占空间

### 3. 左侧底部语言/主题区紧凑化

处理方式：

1. 保留为最后处理的实验项
2. 如果效果不好，直接放弃

## Phase 1：统一运行状态总览

## 目标

让 WSL / Linux 用户进入 Web 页面后，可以直接知道：

1. core 是否正常
2. local gateway 是否正常
3. 当前访问模式是否为补充入口

## 任务

1. 设计一个轻量 runtime 状态总览区
2. 明确状态源来自 Go core API
3. 区分 core 和 local gateway 状态
4. 避免让用户把“core 可访问”误解成“全部已就绪”

## 约束

1. 只改 Web 端
2. 不影响桌面端现有头部和状态区

## 验收标准

1. Web 首页或关键页面可直接看到运行状态总览
2. 用户不需要先看终端日志就能知道系统当前状态

## Phase 2：Tools 页状态语义修正

## 目标

让 `Tools` 页顶部状态表达更准确，不再把“core 可连接”笼统显示成“全部运行中”。

## 任务

1. 审视当前 `Tools` 页顶部状态表达
2. 明确是否改为：
   1. `core 已连接`
   2. `local gateway 状态`
3. 保持工具配置能力逻辑不变

## 约束

1. 只改 Web 端 `Tools` 页显示语义
2. 不改桌面端 `Tools` 页现有交互

## 验收标准

1. `Tools` 页顶部状态不会误导用户
2. 用户能够区分 core 状态和 local gateway 状态

## Phase 3：小屏 / 窄屏导航优化

## 目标

让 Web 端在较窄窗口或移动端下仍然具备基本可用性。

## 任务

1. 评估当前双栏布局在小屏下的问题
2. 设计轻量导航收敛方案
3. 优先采用低风险改法，例如：
   1. 折叠菜单
   2. 抽屉式导航
   3. 更紧凑的侧栏布局

## 约束

1. 不改变桌面端导航结构
2. 不引入重型 UI 组件库

## 验收标准

1. 窄屏下页面仍能顺利切换模块
2. 菜单和主要操作不会相互挤压到不可用

## Phase 4：清理 Web 端残留桌面心智

## 目标

让 Web 端代码和交互更纯粹，不再长期维持“桌面兼容式 null 传参”。

## 任务

1. 梳理 Web 页面中仍然残留的桌面端 props / 分支
2. 逐步让 Web 端依赖显式 HTTP API 数据
3. 清理不必要的桌面壳兼容痕迹

## 约束

1. 不为了清理心智去重构整个目录结构
2. 不引入新的抽象层

## 验收标准

1. Web 端页面来源更清晰
2. `desktopState === null` 这类兼容写法减少

## Phase 5：文档补充与可选实验项

## 目标

补完文档闭环，并只在最后视情况尝试低优先级实验项。

## 任务 A：补 `ai-mini-gateway` 二进制准备说明

需要补充：

1. 二进制从哪里获取
2. 如何构建
3. 推荐放置位置
4. 如何对应到 `LOCAL_GATEWAY_RUNTIME_EXECUTABLE`

## 任务 B：评估 `GATEWAY_BIND`

只做评估，不默认实现。

需要回答：

1. 是否真的有必要开放配置
2. 默认安全边界是否仍然保持 `127.0.0.1`
3. 是否会增加误暴露风险

## 任务 C：左侧底部语言/主题区紧凑化实验

这项只在前面所有主项完成后再考虑。

规则：

1. 仅限 Web 端
2. 如果效果不如当前版本，直接取消
3. 不允许带动桌面端样式一起调整

## 验收标准

1. 文档对部署和二进制准备更闭环
2. 实验项不会影响主链路稳定性

## 实际开发顺序建议

如果进入代码修改，建议严格按这个顺序：

1. 先做 Web 端统一运行状态总览
2. 再做 `Tools` 页状态语义修正
3. 再做小屏 / 窄屏导航
4. 再清理 Web 端残留桌面心智
5. 最后补文档和实验项

## 禁止事项

本轮开发过程中禁止：

1. 改动桌面端稳定功能
2. 修改桌面端交互以迁就 Web 端
3. 引入新的服务层
4. 引入新的重型状态管理方案
5. 借 polish 名义做大规模重构
6. 把 Web 端补充入口继续向主入口方向扩张

## 每阶段完成定义

一个阶段只有在满足以下条件后才算完成：

1. 代码或文档修改已完成
2. 与本阶段相关的 Web 端行为已验证
3. 没有破坏桌面端已有能力
4. 阶段结论已同步回文档

## 最终完成标准

这轮 polish 完成后，理想状态应是：

1. WSL / Linux 用户能更容易理解当前系统状态
2. Web 端状态表达更准确
3. 小屏下基本可用
4. Web 端代码的桌面心智残留更少
5. 桌面端功能完全不受影响
